# Loci Markdown 记忆生成协议

- 思想来源：[`codesstar/loci`](https://github.com/codesstar/loci)
- 本文目标：只靠这一份文档，就能复刻同一套 Markdown 记忆生成思想
- 本文不是：Loci 安装器、Dashboard、Node 守卫脚本、Claude Code hook 的产品说明书
- 本文是：把对话变成可持久化、可分层加载、可跨会话复用的 Markdown 的完整协议

把这份文档交给人或 Agent 时，应按「协议」执行，而不是按「灵感」自由发挥。若某条规则与本地习惯冲突，先遵守本文，再显式修订协议本身。

---

## 0. 如何使用这份文档

### 0.1 给人看

按这个顺序落地：

1. 先背下第 2 节公理，不要先建一堆空文件。
2. 建第 7 节目录，文件先放模板，不要先填内容。
3. 用第 5、6 节处理每一轮对话。
4. 用第 10 节模板写文件。
5. 用第 22 节检查清单验收。

### 0.2 给 Agent 看

不要把本文整篇贴进系统提示词。正确用法见 [`loci-memory-usage.md`](loci-memory-usage.md)：常驻短规则负责提醒检查信号，`markdown-memory` skill 负责写对文件。

每个会话开始时：

1. 先加载 L1 文件（见第 8 节），不要把整座记忆宫殿塞进上下文。
2. 先回答用户，再按第 5 节做信号检查。
3. 有信号才蒸馏、路由、写入；无信号不写。

### 0.3 成功标准

一套实现算「复刻成功」，当且仅当同时满足：

- 不保存原始对话全文。
- 每条记忆都能回答：这是什么类型、为什么值得留、写在哪个文件、当前态还是历史。
- 下次新会话只读少量 L1，就能接手，不必翻聊天记录。
- 当前文件保持短，历史只追加。
- 项目细节不进大脑仓库，大脑只保留索引。

## 1. 一句话定义

**Markdown 记忆不是聊天归档，而是把未来还会用到的结论，蒸馏成结构化、可路由、可分层加载的短文件。**

半小时对话可能只变成：

- 1 份决策（背景 / 选项 / 决定 / 后续）
- `learned.md` 里 1 条可复用教训
- `insights.md` 里 1 条尚在观察的洞察
- 1 条待办
- 操作总账里 1 行

也可以什么都不写。没有信号，就不生成 Markdown。

## 2. 核心公理

下面 12 条必须全部遵守。删掉任何一条，生成出来的就不再是这套思想。

1. **蒸馏，不堆积。** 禁止把原始对话、会议录音稿、聊天记录原文写进记忆文件。只提取未来 Agent 知道了会明显更有用的结论。
2. **先分类，再落点。** 不存在一个无限追加的 `memory.md`。类型决定路径。路径错了，内容写得再好也算生成失败。
3. **当前态要瘦，历史要长。** 当前文件只保留「现在仍然为真、现在仍然指导行为」的内容。过期内容追加到历史，或移入归档，不在当前文件里堆积。
4. **分层加载，不是分层存储。** 所有文件都可以在磁盘上。分层管的是「什么时候读进模型」。
5. **汇聚，不占有。** 大脑是索引和理解层，不是仓库。严肃项目的完整记忆属于项目自己；外部笔记只存指针。
6. **先回答，后记忆。** 记忆像呼吸，不举手打断。主回复必须先处理用户问题，写入在后台完成，确认最多一句人话。
7. **没有信号，就不保存。** 闲聊、重复已知事实、一次性情绪、纯过程噪音，一律不写。
8. **事实自动写，主观先问。** 稳定事实、明确任务、明确决策、明确偏好，自动蒸馏。敏感、模糊、重大方向、短暂情绪，先确认再写。
9. **归档，不删除。** 过期内容改状态并移入 `archive/`。默认不删文件。
10. **每条记忆可追溯。** 蒸馏时用 HTML 注释标注来源和时间。整合时洞察必须引用源文件。
11. **对用户说人话。** 不主动暴露路径、层级名、inbox、distill、L1 等内部词，除非用户在问系统本身。
12. **当前文件就地更新，历史文件只追加。** `identity.md` / `values.md` / `plan.md` / 项目 `memory.md` 是当前态，就地改。`evolution.md` / 旧决策 / 月度流水 / 操作总账只追加。

## 3. 系统隐喻

把它想成记忆宫殿，不要想成网盘。

- 宫殿大门：`plan.md` + `preferences.md`。每次进门必看。
- 房间索引：`projects/index.md`。告诉你有哪些房间、门在哪。
- 房间本身：各项目仓库里的 `.loci/` 或等价目录。细节在房间里，不搬到大门。
- 日记柜：决策、洞察、教训、流水。默认不上桌。
- 废纸篓式inbox：随手碎片。定期整理，不进大门。

生成 Markdown 时，先问「这张纸条该钉在大门、放进房间，还是塞进抽屉」，再动手写。

## 4. 生成总流程

每一轮用户消息之后，按这个顺序，不可跳步。

```text
用户发言
  → 先给出对用户有用的回答
  → 轻量信号检查
       ├─ 无信号 → 不写文件，结束
       ├─ 明确信号 → 蒸馏 → 路由 → 写入 → 可选一句确认
       ├─ 用户明确要求记住 → 除非不安全或做不到，否则写入
       ├─ 不确定 / 敏感 / 重大 → 先问，再写
       └─ 用户说撤销 → 回滚最近一次写入
  → 若发生了大脑写入 → 追加一行操作总账
  → 若写了决策 → 做 L1 上浮检查
```

禁止的顺序：

- 先说「已保存到 xxx.md」再回答问题。
- 先把整段对话追加到某个 md，再想怎么分类。
- 先写文件再问用户这是不是决策。

## 5. 信号驱动写入

### 5.1 什么是信号

信号 = 这段话里出现了「未来会话还需要的、当前文件里还没有的、足够稳定或足够可执行的信息」。

### 5.2 自动保存的信号

出现以下情况，蒸馏后直接写，不必先问：

| 信号 | 例子 | 落点 |
|---|---|---|
| 明确任务 | 「明天 9 点交材料」 | 任务 |
| 明确日程占用 | 「下午 3 点开会」 | 日程，不是任务 |
| 明确决策及理由 | 「就用 Postgres，不用 Mongo」 | 决策文件 |
| 交互偏好 | 「以后叫我老板」「回复短一点」「别用 emoji」 | `me/preferences.md`，且当轮回复必须已经遵守 |
| 稳定事实 | 「我在济南」「我做后端」 | `me/identity.md` |
| 有用的外部链接/资料 | 「这个文章不错，存一下」 | 收藏/碎片 |
| 项目里以后还要用的事实 | 「这个仓库默认 Node 20」 | 项目 profile 或 memory |

### 5.3 必须先问再写的信号

| 信号 | 原因 |
|---|---|
| 模糊念头，可能明天就变 | 避免污染当前态 |
| 敏感个人信息、财务、健康细节 | 隐私 |
| 人生方向、战略级选择 | 写错代价高 |
| 情绪宣泄 | 可能是暂时的 |
| 意图不清 | 可能是任务、也可能只是发牢骚 |

### 5.4 明确不写的信号

- 用户在重复系统已经知道的事实。
- 纯过程：「我先打开编辑器看看」。
- 一次性情绪：「今天好烦」，且没有形成原则或决策。
- 调试噪音、临时试错、还没选的方案清单。
- 整段聊天记录。
- 已经写过、没有新信息的内容。

### 5.5 确认话术

记忆确认必须短、自然、对人，且从属于主回答。

好：

- 「记住了：明天下午 3 点看路演材料。」
- 「这个决策我记下来了：先支持 Claude Code。」
- 用户说「以后叫我老板」→「记住了，老板，以后就这么叫。」（当轮已遵守）

坏：

- 只回「已保存。」
- 「已蒸馏到 `decisions/2026-09-15-xxx.md`。」
- 「我把它放到 L1 的 preferences 里了。」

偏好类信号有一条硬规则：**承认偏好的那句话，必须已经按新偏好说话。** 禁止「好的记住了」下一轮才改口。

### 5.6 撤销

- 「撤销 / undo」回滚**当前会话最近一次**保存。
- 一次保存改了多个文件，默认全部回滚。
- 用户可指定：「撤销任务，保留决策」。
- 更早的保存不走口头撤销，改文件或看 git 历史。
- 撤销不依赖 git。

## 6. 蒸馏判定

每条候选信息先过这三问。三问都过，才允许生成 Markdown。

### 6.1 未来有用测试

> 未来的 AI 如果知道这件事，会不会明显更有用？

- 会 → 继续。
- 不会 → 丢弃。
- 不确定 → 先问，或放 inbox，不进当前态。

### 6.2 压缩测试

蒸馏后的文本必须比原文短，且能独立阅读。合格形态：

- 1 条结论
- 为什么
- 必要的限制条件
- 可选的后续动作

不合格形态：

- 对话逐句转写
- 「我们讨论了 A、B、C」这种会议纪要腔
- 没有结论的方案罗列

### 6.3 粒度测试

一条记忆 = 一个可独立理解的结论。

- 一次对话做出两个不相关决策 → 两个文件，不要揉在一起。
- 一个决策有多个理由 → 仍是一个决策文件，理由写在 Decision 里。
- 一个新偏好 → 只改 `preferences.md` 对应小节，不要新开文件。

### 6.4 蒸馏等级

按信息价值压缩，不要一律写长文。

| 等级 | 适用 | 生成结果 |
|---|---|---|
| 最小 | 改称呼、改语气、补一个电话 | 原文级别的短句，就地更新 |
| 平衡（默认） | 大多数决策、教训、任务 | 模板填满，但每节只有必要句子 |
| 详细 | 重大技术选型、人生方向 | 完整背景、选项、取舍、后续 |

禁止把最小信息写成详细决策，也禁止把重大决策缩成一行 inbox。

## 7. 路由总表

这是生成思想的心脏。写之前必须先路由。

### 7.1 主路由

| 信息类型 | 判定口诀 | 落点 | 写法 |
|---|---|---|---|
| 怎么跟我说话 | 「以后都要这样」 | `me/preferences.md` | 祈使句，就地更新 |
| 我是谁 | 稳定身份事实 | `me/identity.md` | 就地更新，保持短 |
| 我信什么 | 已稳定、能指导决策的原则 | `me/values.md` | 编号原则，不写新鲜感想 |
| 身体/精力/睡眠 | 会影响工作和判断的状态规律 | `me/wellbeing.md` | 当前规律，不是病历 |
| 今天刚想到 | 新鲜反思，还不稳定 | `me/insights.md` | 五段式，状态先标 observing |
| 以后别再踩 | 可复用教训、方法、错误 | `me/learned.md` | 追加条目，带反例 |
| 我变成了谁 | 身份/价值观/行为发生实质变化 | 先改当前文件，再追加 `me/evolution.md` | 只追加 old/new/reason |
| 人生方向与目标 | 北极星、年度目标、反目标 | 根目录 `plan.md` | 就地更新进度 |
| 跨项目/作为一个人的选择 | 拿走项目后仍重要 | 大脑 `decisions/YYYY-MM-DD-slug.md` | ADR 四段式 |
| 项目内技术/产品选择 | 拿走项目后不再重要 | 项目 `decisions/` | 同样 ADR，不复制进大脑 |
| 明确待办 | 要完成的事 | 任务源（JSON 或任务文件） | 不要写成日记 |
| 占用时间的块 | 会议、课、吃饭、出行 | 日程 | 不要自动镜像成任务 |
| 还没想清楚的念头 | 不是项目，也还不是任务 | `inbox.md` | 一行一条 |
| 可能成为项目、但还没认真做 | 雏形 | `projects/side.md` | 短条目 |
| 认真在做的项目 | 已投入、有决策、会反复回来 | 项目自己的 memory/profile/progress/decisions；大脑只有索引行 | 禁止把全文拷进大脑 |
| 别人的文章/链接/金句 | 来自外部 | `references/` | 指针 + 一句话用途 |
| 自己写的笔记 | 来自自己 | `notes/index.md` 一行，正文尽量留在原处 | 汇聚不占有 |
| 调研材料 | 证据，不是决定 | `notes/research/` | 决策文件可以引用它，它自己不能冒充决策 |
| 值得记住的人 | 合作者、客户、重要联系人 | `people/<name>.md` | 人卡 + 互动日志 |
| 两个人的关系 | 任何同时提到两个人的关系句 | 人卡 **加上** 关系边 | 只写人卡算没写完 |
| 值得记住的地点 | 家、公司、常去的地方 | `places/<slug>.md` | 地点卡 |
| 今天发生了什么 | 当日回顾 | 日记 / daily note | L3，不进 L1 |
| 系统改了哪些记忆 | 审计 | 操作总账 | 永远写，永远不自动读 |

### 7.2 易混分流

这些是最容易写错的地方，写错就不是这套思想。

**任务 vs 日程**

- 任务 = 要完成的事。即使带时间，时间也只是任务属性。
- 日程 = 这段时间被占用。开会、上课、吃饭、出行。
- 「明天 9 点发材料」→ 任务，不自动画到日历。
- 「3 点开会」→ 日程。
- 只有用户明确要挡住这段时间，才把任务拉进日程。

**inbox vs side**

- inbox：念头 / 待办碎片。
- side：潜在项目。看起来像一个可以做起来的东西，但还没认真做。

**碎片 vs 笔记 vs 决策 vs 任务**

- 随手一句话、收藏链接、截图 → 碎片。
- 用户自己写的、有标题的内容 → 笔记指针。
- 有取舍、选了 X 不选 Y → 决策。
- 有时限、可执行 → 任务。
- 形成了可复用原则 → 洞察或教训，不是碎片。

**调研 vs 决策**

- 竞品分析、学习笔记、原始文档 → 研究材料。
- 真正做了权衡并选定方向 → 另写决策，并引用研究材料。
- 禁止把调研文件直接放进 `decisions/`。

**人 vs 任务属性**

- 第一次在任务里提到的人/地点，不要自动建卡。
- 测试：把任务拿掉，这个人/地点还有独立意义吗？没有 → 只当任务字段。
- 「我家在 X」「我认识了 X」→ 直接建卡，因为这句话本身就是稳定事实。
- 同一未建卡对象反复出现 2–3 次，才在对话结尾问一次要不要存。被拒绝后不再问。

**项目决策 vs 大脑决策**

测试句：

> 把这个项目整个拿走以后，这个决定还重要吗？

- 否 → 项目决策。这是默认。
- 是 → 大脑决策。方向、方法论、做不做某类事。
- 不确定 → 默认留项目，不要问，也不要复制一份到大脑。

## 8. 三层加载

生成时就要想「这文件以后怎么被读」。读的方式反过来约束写的长度。

### 8.1 层定义

| 层 | 何时读 | 写什么 | 长度约束 |
|---|---|---|---|
| L1 | 每个会话开始 | 规则、`plan.md`、当前任务快照、项目索引、`preferences.md`、当前状态 | 必须能快速读完。preferences 建议不超过约 30 行，超出细节下沉到 identity |
| L2 | 聊到再读 | 模块说明、具体项目 memory、inbox、references、notes、其余 `me/` | 单文件仍然短；靠索引找 |
| L3 | 用户明确问历史才读 | archive、旧决策、evolution、旧日记、操作总账 | 只追加，不怕长，但不要进 L1 |

### 8.2 会话缓存

- 会话开始时新鲜加载一次 L0/L1。
- 同一会话中，未变化的启动文件不要每轮重读。
- 只有上下文可能过期、刚写过、或用户在问「现在/今天/最新」时，才重读最小相关文件。
- 不要为了「保险」把 L2/L3 预加载进来。

### 8.3 写 L1 的额外约束

L1 只允许放：

- 规则
- 索引
- 当前行动摘要
- 真正重要、每轮都要用的个人上下文（几乎只有 preferences）

禁止放进 L1：

- inbox 碎片
- 完整决策正文
- 项目完整记忆
- 日记
- 操作总账
- 收藏夹正文

### 8.4 L1 上浮检查

每写完一个决策，问：

> 这件事会不会改变当前行为？

- 会 → 把**最小结论**写到最小的 L1 表面：
  - 人生策略/原则 → `plan.md`
  - 行动优先级变化 → 当前任务快照
  - 项目里程碑/洞察 → `projects/index.md` 一行
  - 项目当前状态 → 项目 `memory.md`
- 不会 → 全文留在 L3 决策文件，不再复制。

上浮的是一行摘要，不是把决策文件拷进 L1。

## 9. 当前态与历史

这是 Markdown 能长期给模型用的关键。违反它，文件会在几个月后不可读。

### 9.1 当前文件

就地更新，始终代表「现在」。

- `me/identity.md`
- `me/preferences.md`
- `me/values.md`
- `me/wellbeing.md`
- `plan.md`
- `projects/index.md`
- 项目 `memory.md`
- 项目 `profile.md`
- `tasks/active.md`（若使用）

当前文件里禁止保留：

- 「曾经想过但已放弃」且没有标明过期
- 一长串已完成任务
- 已推翻的决策全文
- 过时的 Next 步骤

### 9.2 历史文件

只追加，不改写旧条目。

- `me/evolution.md`
- `me/insights.md`（条目追加；状态可改）
- `me/learned.md`（条目追加）
- `decisions/`（一个决策一个文件，文件本身尽量不改结论，只更新 follow-up 勾选）
- 项目 `progress/YYYY-MM.md`
- 操作总账 `.loci/activity/YYYY-MM.md`
- 日记

身份变了的标准动作：

1. 改当前文件（例如 `identity.md`）
2. 在 `evolution.md` 追加：日期、旧、新、原因
3. 不要只改当前文件导致历史消失
4. 不要只追加历史导致当前文件仍是旧身份

### 9.3 项目重启文件的瘦身

项目 `memory.md` 是重启表面，不是项目史。

- 通常不超过约 150 行。
- Recent Progress 只留最近 3–7 条有意义进展。
- Active Decisions 只留仍影响当前工作的决策链接。
- 完整流水去 `progress/`。
- 稳定属性去 `profile.md`。
- 超过约 120 行，应整理：重写 memory 为当前接手状态，历史留给 progress。

## 11. Frontmatter 公约

内容文件用 YAML 头。生成时必填能填的字段，不要留空模板腔。

### 11.1 通用字段

```yaml
---
created: YYYY-MM-DD          # 或 ISO 8601
updated: YYYY-MM-DDTHH:MM:SS+TZ
date: YYYY-MM-DD             # 决策、日记用 date
tags: []
status: active               # template | active | done | archived | dormant
---
```

### 11.2 状态机

| status | 含义 | 生成时怎么用 |
|---|---|---|
| template | 还没初始化 | Agent 看到应提示先完成设置，不要当真实记忆读 |
| active | 当前有效 | 默认 |
| done | 当日/当周已结束 | 日计划 |
| dormant | 项目暂停 | 索引条目 |
| archived | 过期，已搬家 | 同时加 `archived: YYYY-MM-DD` |

### 11.3 敏感度（可选但应保留字段语义）

```yaml
sensitivity: medium     # high / medium / low / public
ai-context: allow       # allow / summary-only / deny
```

默认建议：

| 目录 | sensitivity | ai-context |
|---|---|---|
| `me/` | medium | allow |
| `finance/` | high | deny |
| `tasks/` | low | allow |
| `people/` | high | summary-only |
| `decisions/` | medium | allow |
| `references/` | low | allow |

生成财务、人脉类 Markdown 时，不要把完整账号、精确余额、隐私联系方式写进会进云端上下文的正文。需要时只写摘要。

### 11.4 来源标注

蒸馏进文件的关键句，后面加：

```markdown
改用 GraphQL，不再用 REST <!-- source: conversation @2026-03-11T14:32 -->
```

整合产生的洞察，必须引用源文件：

```markdown
- [pattern] 最近三个决策都在做减法 <!-- source: decisions/2026-03-09-api-simplify.md @2026-03-09T14:32, decisions/2026-03-10-drop-graphql.md @2026-03-10T16:05 -->
```

时间戳用途：

- 回答「上周三下午在干什么」
- 判断因果顺序
- 回答「我为什么决定 X」时能沿来源回溯

## 12. 各文件生成规格

以下每一小节都是「必须按此生成」。结构可变通的只有用词，字段和职责不能丢。

---

### 12.1 `me/preferences.md`（L1）

**职责**：告诉 Agent 怎么跟用户说话、怎么交付工作。不是身份传记。

**触发**：以后叫我… / 回复短一点 / 用中文 / 别用 emoji / 写文档要先 TL;DR / 外发先给我看草稿。

**写法**：短、祈使句、可执行。超过约 30 行，细节搬到 `identity.md`。

**结构**：

```markdown
---
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: [preferences, core]
status: active
---

# How to Work With Me

## Address Me As
## Language & Tone
## Reply Style
## Work
## Do / Don't
```

**好**：

```markdown
## Address Me As
- 叫我 **林舟**，不要叫全名或「用户」

## Language & Tone
- 中文；直接、短；不要客服腔

## Reply Style
- 先给结论，细节等我问
- 不要 emoji

## Work
- 文档开头先写一段 TL;DR
- 对外邮件先出草稿，我自己发

## Do / Don't
- Do: 计划拍板前先反驳我的假设
- Don't: 能异步就不要建议开会
```

**坏**：把童年经历、技术栈偏好、人生目标写进来。那些分别属于 identity / learned / plan。

**当轮生效**：写入与遵守必须发生在同一轮回复。

---

### 12.2 `me/identity.md`

**职责**：稳定的「我是谁」。给 Agent 正确的人设，不是流水账。

**写**：姓名/称呼以外的身份、职业、地点、背景、当前阶段、工作方式。

**不写**：怎么称呼我（那是 preferences）、今年 KPI（那是 plan）、昨天心情。

**结构**：

```markdown
# Who I Am

## Basic Info
## Current Season
## Working Style
```

Basic Info 用字段列表。Current Season 用一段现在进行时。Working Style 写可观察习惯，不写鸡汤。

**好**：

```markdown
- **职业**：后端，兼职做自己的监控产品
- **当前阶段**：产品还在内测，用兼职养活自己
```

**坏**：把三年前每份工作的周报粘进来。

---

### 12.3 `me/values.md`

**职责**：已经稳定、能拿来做决定的原则。

**硬规则**：新鲜想法不得直接写入。先在 `insights.md` 观察，用户明确说这是原则，或多次被决策引用后，再升级。

**写法**：编号，一条一个原则，名称 + 一句为什么。通常 5–9 条。不要写成博客。

**好**：

```markdown
1. **先发布，再完美** — 未上线的 100 分，不如已上线的 80 分。
```

**坏**：

```markdown
今天突然觉得还是应该注重品质……（这是 insight，不是 value）
```

---

### 12.4 `me/wellbeing.md`

**职责**：身体、睡眠、精力、情绪规律中，会影响判断和安排的部分。

**写原则和规律，不写医疗档案。**

结构建议：Body / Sleep & Energy / Mental State / Principles。

**好**：「连续两晚睡不好，产品判断会发飘。睡眠是工作输入，不是奖励。」

**坏**：把体检指标、用药细节在无必要且未允许时写入会进云端上下文的文件。

---

### 12.5 `me/insights.md`

**职责**：新鲜个人反思。这是「观察室」，不是「宪法」。

**每条必须有五段**：

```markdown
## YYYY-MM-DD — 短标题

**背景**：什么证据触发了这个想法。
**洞察**：压缩后的那一句。
**为什么重要**：对这个人意味着什么。
**暂定影响**：以后可能怎么改行为。
**状态**：observing | promoted-to-values | promoted-to-learned | expired
```

状态机：

- 新条目默认 `observing`
- 变成可复用方法 → 把结论写入 `learned.md`，本条改为 `promoted-to-learned`
- 变成稳定原则 → 写入 `values.md`，本条改为 `promoted-to-values`
- 过时或证伪 → `expired`，不要删

**好**：洞察是一句可证伪的判断，背景能指向最近的决策或行为。

**坏**：只有金句没有背景；或直接把洞察抄进 values。

---

### 12.6 `me/learned.md`

**职责**：付过学费的、下次还要用的教训。

**写法**：按主题分组。每条包含：

- 结论
- 怎么学到的（反例或故事，要短）
- 以后怎么做

**好**：

```markdown
### 不要过早抽象
先做第一个真实用例。同一模式重复 3 次再抽象。曾经为没有用户的管道做了一周通用层，前 3 个用户全要不同的东西。
```

**坏**：把「今天修了个 bug」写成教训，却没有可复用方法。

---

### 12.7 `me/evolution.md`

**职责**：身份、价值观、健康观、行为发生实质变化时的时间线。只追加。

**格式**：

```markdown
### YYYY-MM-DD | 短标题
旧：……
新：……
原因：……
```

也可以把旧/新/原因写成一段，但三者信息都不能缺。

只在「当前文件已经改过」之后追加。禁止只在 evolution 里宣布变化、当前文件却没改。

---

### 12.8 `plan.md`（L1）

**职责**：北极星。日常任务应能回溯到这里。目标不放 `me/goals.md`。

**结构**：

```markdown
# Life Direction & Goals

## Mission
## 3-Year Vision
## 本年目标
### Goal N
- Key result
- Progress
## 当前季度焦点
## Anti-Goals
```

Anti-Goals 是这套思想的一部分：明确不做什么，防止记忆系统变成欲望清单。

进度用现在时短句更新，不要把计划写成已完成日记。

---

### 12.9 决策文件

文件名：`YYYY-MM-DD-slug.md`  
一个决策一个文件。这是 ADR，不是日记。

**模板（大脑和项目共用）**：

```markdown
---
date: YYYY-MM-DD
tags: []
status: active
---

# Decision: 标题要用结论，不要用「关于 XX 的讨论」

## Background
为什么必须现在做这个选择。只写迫使决策发生的约束。

## Options
1. **方案 A** — 一句话利弊
2. **方案 B** —
3. **方案 C** —

## Decision
选了什么。
### Reasoning
为什么。
### Trade-offs Accepted
接受了哪些代价。被拒绝的选项必须留下，否则下次会重新吵一遍。

## Follow-up
- [ ] 后续动作
```

**生成规则**：

- 标题即结论：`Raise Rate to $165/hr`，不是 `Pricing thoughts`
- 至少 2 个真实选项。只有一个选项的不叫决策，叫记录
- 没做权衡就不要生成决策文件，去 inbox 或 research
- Follow-up 用 checkbox，完成后勾选，不要因此新开决策
- 决策结论本身尽量不改写；若被推翻，新写一份决策，旧文件 status 改为 archived，并互相链接

**好标题**：`Decision: 监控存储选 TimescaleDB，不选 ClickHouse`  
**坏标题**：`Decision: 技术栈讨论`

---

### 12.10 `inbox.md`

**职责**：低摩擦捕获。不是任务系统，不是项目库。

```markdown
---
updated: YYYY-MM-DD
---

# Inbox

## Unprocessed
- 一行一条，动词或名词都可以，先抓住
```

规则：

- 不要在捕获时分类。
- 超过 10 条新条目，在**对话结束时**问要不要整理，不要一开场就问。
- 对人说「待办里积了不少东西」，不要说 inbox。
- 整理时：可执行且有时限 → 任务；有取舍 → 决策；仍是念头 → 留着；已解决 → 归档或删除该行。
- 超过 20 条时，无日期的 14 天以上条目可归档，并在日记里留一句，让用户知道。
- **不要自动把 inbox 加载进 L1。**

---

### 12.11 `projects/index.md`

**职责**：认真项目的灯光索引。禁止变成项目数据库。

```markdown
## project-name   <!-- status: active | dormant | archived -->
一句话本质。repo: <path>。memory: <repo>/.loci/memory.md
Key decisions: [[仅当有大脑级决策时]]
[insight] / [milestone] 只写一行摘要，指向项目内文件
updated: <ISO8601>
```

只在这些情况更新索引：

- 新连接一个认真项目
- 项目出现对仓库之外也有意义的 `[insight]` / `[milestone]`
- 状态变为 dormant / archived

禁止：把项目 memory 全文复制过来。

---

### 12.12 `projects/side.md`

**职责**：项目孵化器。

```markdown
## Incubating
### 名称 — 一句话 + 当前状态。[ISO8601 added]

## Archive
刻意不做或做过又放下的雏形
```

毕业条件：用户决定认真做。然后才在项目仓库建立完整记忆，并在 index 加一行。不要提前建项目宫殿。

---

### 12.13 项目 `memory.md`

**职责**：下次打开这个项目时，5 分钟内能接手。给 AI 读，也给 AI 写。

```markdown
---
project: <name>
description: <one-line>
brain: <brain-path>
status: active
created: <ISO8601>
updated: <ISO8601>
---

# <Project Name>
> 一句话 · repo: <path>

## Goal
## Current State
## Now / Next
## Recent Progress
- YYYY-MM-DD HH:MM · 面向结果的短更新
## Active Decisions
- [决策标题](./decisions/YYYY-MM-DD-slug.md)
## Risks / Open Questions
## Pointers
```

Now / Next 只留 1–3 件立刻要做的事，就地覆盖，不追加成流水。

Recent Progress 满 3–7 条就淘汰最旧的；被淘汰的内容必须已经存在于 `progress/`。

---

### 12.14 项目 `profile.md`

**职责**：稳定属性。不随每天进度改。

```markdown
## What This Is
## Scope          # 做什么 / 不做什么
## Milestones     # - YYYY-MM[-DD] · 名称 · done|next|planned
## Key People     # - 名字 · 角色
## Files          # - 名称 · 路径或 URL
## Conventions    # 命名、技术约束、稳定规则
```

进度变化不要写这里。里程碑状态可以改，过程细节不行。

---

### 12.15 项目 `progress/YYYY-MM.md`

只追加：

```markdown
## YYYY-MM-DD
- HH:MM · 发生了什么（结果导向，不要「看了一下代码」）
```

---

### 12.16 `people/<name>.md`

```markdown
---
name:
relation:
tags: []
last_contact:
created: YYYY-MM-DD
---

# Name

## How We Met
## Contact Info
## Notes
## Interaction Log
- YYYY-MM-DD · 发生了什么
```

关系边是强制的：句子里出现两个人，就必须写边。创建人卡不等于记录关系。

「认识了乙，他是甲的朋友」= 两笔：建乙的人卡 + 甲乙朋友边。写完后必须回看原句，有第二个名字却没边，就不算写完。

---

### 12.17 笔记与收藏

**外部笔记**：默认只在 `notes/index.md` 写一行：

```markdown
- 标题 · 链接或路径 · 一句话它是什么 · #tags
```

正文留在 Obsidian / 飞书 / Notion。大脑不吞全文。

**短即时笔记**：`notes/<slug>.md`，frontmatter 含 title / tags / created，同时在 index 补指针。

**收藏条目**：

```yaml
---
date: YYYY-MM-DD
type: article    # article | book | video | quote | product | idea | tweet | paper
source: "https://..."
tags: []
one-line: "一句话结论"
use-for: "以后用在什么决策/项目上"   # 最重要的字段
status: raw      # raw → processed → applied → archived
---
```

`use-for` 是收藏类 Markdown 的灵魂。没有它，收藏只是书签，不能被主动召回。

捕获时可以先扔 `references/inbox.md`，不分类。超过 10 条再整理成独立条目。

工作中若当前主题命中 tags 或 use-for，可在自然停顿时提一句「你以前存过一篇关于 X 的」。同一会话不提第二次。

---

### 12.18 日计划 `tasks/daily/YYYY-MM-DD.md`

这是当天的计划与回顾，**不是任务源**。任务另有源。禁止把任务复制一份到 daily 当主存储。

```markdown
---
date: YYYY-MM-DD
mood:
energy:
tags: [daily]
---

# YYYY-MM-DD Daily Plan

## Top 3 Priorities
## Schedule
## Review
- Discussed / Learned / Recorded / Accomplished / Incomplete / Tomorrow
```

---

### 12.19 周复盘

```markdown
## What I Completed
## What I Didn't Complete & Why
## Next Week's Focus
## Inbox Cleanup
```

没完成必须写原因。这是给未来模型避免重复误判的材料。

---

### 12.20 日记

实时：对话中出现决策、新知、重要主题，先往 `journal/buffer.md` 追加 `- [HH:MM] 一句话`。

触发「总结一下今天」时：读 buffer + 当天上下文 → 生成 `YYYY-MM-DD.md` → 用户确认后清空 buffer。

日记结构：Accomplished / Learned / Discussed / Decisions。

会话开始发现昨天没有日记，可提醒补，不要擅自虚构。

---

### 12.21 当前任务快照 `tasks/active.md`

给 L1 快读的生成视图，不是权威源。若同时有结构化任务数据，以结构化数据为准，Markdown 只做摘要。

按优先级分组，P0 是放下一切也要做的。已完成项不要长期堆在当前快照。

---

### 12.22 操作总账 `activity/YYYY-MM.md`

每次大脑写入之后追加一行。永远写，永不自动读。

```markdown
## YYYY-MM-DD
- HH:MM · 类别 · 一句人话，含可追溯关键词（哪个项目/哪个人）
```

例：`- 21:00 · 决策 · 在 TaskFlow 决定用 PostgreSQL 存文章`

禁止出现文件路径。用户问「今天/这周做了啥」才读。

---

### 12.23 归档

```text
archive/
├── tasks/
├── planning/
├── projects/
└── misc/
```

规则：搬家，不删除；保留原 frontmatter；增加 `archived: YYYY-MM-DD`；只在查历史时读，属于 L3。

## 13. 项目记忆协议

### 13.1 何时开始为项目生成记忆

大脑不是仓库，不要给每个看过一眼的仓库建记忆。两个触发等价：

- 用户说「记住这个项目 / 把这个项目连到大脑」→ 立刻建。
- Agent 观察到项目已经认真起来（有决策、反复回来、有里程碑、明显在投入）→ 在**对话结尾问一次**。被拒绝后永远不再问。

都没触发 → 默认不建。不够认真的放 `side.md`。

### 13.2 指令文件 vs 记忆文件

- `AGENTS.md` / `CLAUDE.md` = 行为规则（怎么读怎么写）
- `memory.md` = 重启上下文（从哪继续）
- `profile.md` / `progress/` / `decisions/` = 细节

不要把行为规则写进 memory，也不要把当前进度写进 AGENTS.md。

### 13.3 项目内标签

可上浮到大脑索引：

- `[insight]` 可复用模式
- `[milestone]` 发布、完成阶段

只留项目内：

- `[decision]` `[architecture]` `[local]` `[debug]` `[wip]` `[private]`

`[private]` 永远不上浮。密钥、凭据、私事禁止进大脑索引。

### 13.4 跨项目流动

项目 → 大脑：只上浮一行 insight/milestone。  
大脑 → 项目：先读 index 找到房间，再按需打开该项目 memory。不要为了同步制造 `to-hq.md` 这类镜像文件。

## 14. 记忆整合

灵感是海马体睡眠整合，不是再存一遍原文。

### 14.1 何时做

- 当天第一次会话可做过去 24 小时的整合。
- 手动：指定 7 天或 30 天。
- 没有新材料：自动模式保持沉默，不要为了交差写空洞察。

### 14.2 看什么

最近的决策、任务完成/新增、me/ 的 updated、操作总账、inbox、相关项目索引。不要扫描所有项目全文。

### 14.3 找什么

- 跨域重复主题
- 自相矛盾（上周说聚焦，这周又新开 3 个项目）
- 动量（连续完成关键任务）
- 跨项目收敛
- 身份/价值观移动
- 相对 plan.md 的目标进度
- 时间分配与口头优先级是否一致
- 过期任务

### 14.4 产出

只往 `insights.md` 追加个人反思，状态先 `observing`。足够稳再升级到 values 或 learned。真的发生了人格/原则变化，才走 evolution。

整合报告对人只说一段话。不要输出扫描了哪些路径。

---

## 15. 写作风格

生成 Markdown 时的文风本身就是协议的一部分。

1. **结论先行。** 标题和首句就要是结论。
2. **带原因。** 没有 why 的记忆，下次无法判断是否过期。
3. **带反例或取舍。** 决策留下没选的路；教训留下踩过的坑。
4. **短。** 当前文件能删则删。能一行说完不要三段。
5. **具体。** 「注意性能」不合格；「p99 要从 800ms 降到 200ms」合格。
6. **现在时描述当前，过去时描述历史。**
7. **不要会议纪要腔。** 禁止「本次会议讨论了以下几点」。
8. **不要对 AI 说话。** 文件是给未来的你和未来的 Agent 读的，用对那个人说话的口吻。
9. **一条一个主题。** 用文件名和标题切开，不要在一个文件里开杂货铺。
10. **用户原话优先于模型猜测。** 用户对收藏的评价写入 note；模型自己的猜测不写。

## 16. 从对话到文件的逐步工作流

把下面当作生成算法。

```text
1. 理解用户本轮要解决的事，先回答。
2. 扫描本轮是否出现第 5 节信号。
3. 对每个信号做第 6 节三问。
4. 用第 7 节路由，得到唯一落点。若可能有两个落点：
     - 决策 + L1 上浮：允许「完整决策 + 一行摘要」
     - 人 + 关系：允许「人卡 + 边」
     - 其余情况选更窄的那个落点，不要双写全文
5. 打开落点文件的模板，只填变化的部分。
6. 当前文件：就地改最小段落。
   历史文件：追加。
   决策：新文件。
7. 打上来源时间戳。
8. 更新 updated / date。
9. 追加操作总账一行。
10. 若是决策，做 L1 上浮检查。
11. 主回答末尾最多一句确认；无信号则完全不提记忆。
```

双写禁令：同一决策全文既放项目又放大脑，是最常见的失败模式。

## 17. 端到端蒸馏示例

以下示例用于对齐「生成出来应该长什么样」。不要把对话原文存进仓库。

### 17.1 输入（对话摘要，仅作说明）

用户：以后叫我舟哥，回复用中文，先说结论。对了，监控库我决定用 TimescaleDB，ClickHouse 运维太重。另外明天 9 点把协议发给客户。突然想到也许可以做 Grafana 插件，先记一下。

### 17.2 信号拆解

| 片段 | 信号 | 落点 |
|---|---|---|
| 以后叫我舟哥，中文，先说结论 | 偏好，自动写，当轮遵守 | `me/preferences.md` |
| 监控库选 TimescaleDB 不选 ClickHouse | 项目内技术决策 | 项目 `decisions/2026-09-15-timescaledb.md` |
| 明天 9 点发协议 | 带时间的任务，不是日程 | 任务 |
| 也许可以做 Grafana 插件 | 未承诺的念头 | `inbox.md` 或项目 side，不是决策 |

### 17.3 应生成的决策（节选）

```markdown
---
date: 2026-09-15
tags: [storage, architecture]
status: active
---

# Decision: 监控存储用 TimescaleDB，不用 ClickHouse

## Background
需要为指标存储做选择。约束：单人维护、要会 SQL、先支持约 1000 人规模。

## Options
1. **TimescaleDB** — Postgres 生态，运维熟悉，时间序列够用
2. **ClickHouse** — 分析更强，但运维和生态更重
3. **纯 Postgres** — 最熟，但保留和连续聚合要自己做

## Decision
选 TimescaleDB。

### Reasoning
单人团队先吃熟悉的生态；不够再在摄入路径补专用组件。

### Trade-offs Accepted
放弃 ClickHouse 在高基数分析上的优势；接受 Timescale 在非时序查询上没那么「原生」。

## Follow-up
- [ ] 建 hypertable 和保留策略
```

同时：

- `preferences.md` 的 Address / Language / Reply Style 就地改，且本轮开头已称「舟哥」。
- 任务新增「发协议给客户」，日期明天 9:00，不写进日历，除非用户要挡住这小时。
- inbox 增加一行 Grafana 插件念头。
- 项目 `memory.md` 的 Current State / Now Next 改成反映已选定存储。
- 大脑 `projects/index.md` **不**复制决策全文。若这只是项目内部选型，索引甚至一行都不用改。
- 操作总账追加三行：偏好、决策、任务。不要为 inbox 写得很正式，一行即可。

### 17.4 明确不生成什么

- 不生成名为「2026-09-15 对话记录.md」的文件。
- 不把 Grafana 插件写成决策。
- 不把 TimescaleDB 决策复制进 `me/learned.md`，除非提炼出跨项目教训，例如「单人团队先选能用 SQL 的存储」。即便如此，也是另写一条教训，不是拷贝决策。

## 18. 反模式清单

出现下列任一情况，说明生成思想已经走样，需要重写，而不是继续追加。

1. 把聊天记录、会议转写、Agent 思考过程写进记忆文件。
2. 只有一个巨大的 `memory.md` / `notes.md` 无限追加。
3. 当前文件超过阅读负担，却还把历史堆在里面。
4. 决策没有选项，或没有写下没选的路。
5. 新鲜感想直接进 `values.md`。
6. 项目全文复制进大脑。
7. inbox 被当成 L1 每轮加载。
8. 任务、日程、日记三者互相同步成三份真相。
9. 对人回复里出现路径、L1、distill、inbox 等内部词。
10. 承认了新偏好，但当轮回复还在用旧称呼或旧语气。
11. 为每个提到的人和咖啡馆自动建卡。
12. 调研材料放进 `decisions/`。
13. 用删除代替归档。
14. 无信号也每天「总结并存档」制造空文件。
15. 同一事实在 identity、plan、项目 memory、inbox 各写一遍且不互相指向。

## 19. 与产品实现的边界

复刻的是思想，不是把 Loci 每一个脚本都搬过来。下面这些是实现细节，可以替换，但替换后必须仍满足公理。

| Loci 实现 | 思想要求 | 可替换为 |
|---|---|---|
| `loci-task.js` 写 JSON | 任务要有单一权威源，Agent 不要手搓坏结构化数据 | 任何带校验的任务存储；Markdown 快照只能当只读视图 |
| Dashboard | 给人看全局 | 不用也行 |
| Claude Code hooks | 会话开始注入 L1 地图 | 任何 Agent 的启动规则 |
| `.loci/` 目录名 | 项目记忆与代码仓库住在一起 | 别的目录名，职责不变 |
| 跨终端 `check-updates.js` | 多会话不要互相覆盖 | git pull/push 或其他同步 |

不能替换掉的：蒸馏、路由、分层、当前态/历史分离、汇聚不占有、信号驱动、来源追溯。

## 20. Git 友好写法

这套 Markdown 天生适合 Git，生成时要让 diff 可读。

- 一个决策一个文件，避免在巨型文件中间插入导致每次 diff 巨大。
- 当前文件就地改同一段落，不要把同一条改成「新追加一条更正」。
- 历史只在末尾追加。
- 列表项一行一条，方便冲突时人工选。
- frontmatter 的 `updated` 允许变；不要为此重排整个文件。
- 不要把本机绝对路径写死在会跨设备同步的索引里，优先仓库名 + 相对路径。需要本机路径时，用每台机器自己的 path map。

## 21. 给 Agent 的最小启动指令

把下面这段放进 `AGENTS.md` 即可驱动生成。细节仍以本文为准。

```markdown
你管理一座分层 Markdown 记忆宫殿。

启动：读 plan.md、me/preferences.md、projects/index.md、当前任务快照。
不要预加载 inbox、日记、旧决策、操作总账。

每一轮：先回答人。再检查是否有可存信号。
无信号不写。有信号则蒸馏（禁止存原文），按类型路由到唯一落点。
当前文件就地更新并保持短；历史只追加。
项目细节写在项目自己的记忆目录；大脑只保留一行索引。
决策用背景/选项/决定/后续。没选的路必须留下。
新偏好当轮生效。确认只用一句人话，不报路径。
写完决策后检查是否要向 L1 上浮一行摘要。
任何写入后在当月操作总账追加一行。
```

## 22. 复刻检查清单

新系统上线前，用真实对话跑一遍，全部勾上才算复刻成功。

- [ ] 一轮闲聊，零文件变化
- [ ] 「以后叫我 X」，preferences 已改，且本轮已用新称呼
- [ ] 一个带时间的任务，没有被自动画进日程
- [ ] 一个会议，进了日程，没有变成待办
- [ ] 一个真正决策，生成了四段式文件，含未选方案
- [ ] 同一决策没有在大脑和项目各存全文
- [ ] 一个「也许可以做」的念头进了 inbox 或 side，没有进 decisions
- [ ] 一篇外部文章只存了指针和 use-for，没有全文
- [ ] 项目 memory 仍短，progress 有追加
- [ ] insights 五段齐全，状态是 observing
- [ ] 价值观没有被当天感想污染
- [ ] 身份变更同时改了 identity 和 evolution
- [ ] L1 文件总长度仍可在一次启动中读完
- [ ] 操作总账有人话行，且启动时没有被加载
- [ ] 对用户的确认里没有路径和内部词
- [ ] 撤销能回滚最近一次写入
- [ ] 归档没有使用删除

## 23. 快速对照卡

生成前默念：

1. 未来有用吗？无用则停。
2. 这是偏好、身份、原则、洞察、教训、目标、决策、任务、日程、碎片、笔记、人，还是项目？
3. 当前态还是历史？
4. 大脑索引还是房间正文？
5. 最短的正确文件是哪一个？

写完再问：

1. 原文还在不在记忆里？应该不在。
2. 明天的模型只看 L1 和这份新文件，能否接手？
3. 三个月后这条还会是真的吗？不是真的就不该在当前文件。

## 24. 本文自我说明

若你改动了路由表、层定义或当前态/历史规则，那就是在创建新思想，不要再声称与 Loci 的 Markdown 生成思想相同。若你只是改了目录名、把任务从 JSON 换成 Markdown、去掉 Dashboard，但 12 条公理仍在，则仍算复刻成功。
